# Journal ingestion design

Updated 2026-11-02. Direct read-only SQLite ingestion replaces the temporary full-database copy. This document records the options, selected behavior, and limitations.

## Privacy boundary

Apple Journal owns the original body, title and attachments. Our persistent SQLite database contains only identifiers, timestamps, HMAC fingerprints, deletion state and synchronization records. The reader has no body export or logging path. Prompt augmentation now assembles selected current bodies in memory only; see PROMPT_AUGMENTATION.md. Original bytes are read transiently by SQLite and fingerprinting; attachments are never opened.

The selected mode allows SQLite's normal read coordination with Apple's WAL/shared-memory files. It does not promise that every supporting file remains byte-for-byte untouched. Journal records, schema, main database and WAL are not explicitly written, migrated, indexed, checkpointed or backed up by this app. The source connection uses SQLITE_OPEN_READONLY, not immutable mode.

## Options and tradeoffs

| Option | Benefits | Costs and risks | Decision |
| --- | --- | --- | --- |
| Direct read-only connection, one read transaction | No full copy, no duplicate body on disk, committed WAL changes visible, consistent view of entries/assets/deletions | Participates in SQLite coordination; may need existing WAL/SHM or permission for sidecar setup; long readers can delay checkpoint progress and grow WAL; busy/permission errors possible | Selected |
| Private disk snapshot (previous implementation) | Source reading can finish before processing; SQLite work isolated to disposable copy | Full DB/WAL disk space and copy time; snapshot contains private content; crash leftovers; signature-guarded file copying is not an atomic snapshot | Removed from runtime; no automatic fallback |
| SQLite backup into memory | Consistent copied database, no application-created content file | Still copies the whole database; memory proportional to source size; OS may swap memory; source coordination still needed | Not selected for large stores |
| Short paged live reads | Shorter read transactions and less checkpoint delay | Pages may represent different moments; concurrent edits/deletions complicate reliable completion and missing-entry reconciliation | Future option only with a correct reconciliation protocol |
| APFS clone/filesystem snapshot | Potentially lower initial copy cost and isolated processing | Still a logical content copy; filesystem-specific; obtaining one coherent DB/WAL view and cleanup requires additional implementation | Not implemented |

Never use immutable=1 for the changing live store: it disables locking/change detection under an assumption that the source cannot change. No option bypasses macOS privacy permissions or makes Apple's private schema a supported API.

## Selected read pipeline

1. Start the synchronous reader on a detached worker task. Check cancellation and open the source read-only. Paths ending in symlinks are rejected by the database wrapper.
2. Install a SQLite progress handler and a monotonic-time read budget (default 60 seconds).
3. Execute BEGIN and read/validate the required schema, establishing one consistent source view.
4. Build TEMP asset_order with only numeric (entry row ID, asset row ID) values. Index those numeric keys in temporary storage. This does not create an index or table in Apple's main database.
5. Enable query_only after preparing TEMP keys. Stream entries by primary key. Walk TEMP keys in indexed order and fetch each source asset by primary key using CROSS JOIN. This avoids sorting full asset records, which could otherwise spill private metadata/title content to disk. No dependency on a pre-existing Apple asset index is required.
6. Hash entry columns and matching asset rows with the unchanged v1 HMAC format. Hold only the current rows and hashing buffers in application memory. SQLite caches/current blobs are additional memory, so this is not a fixed-memory guarantee.
7. Upsert metadata in a separate local database transaction. Track seen UUIDs in a disk-backed metadata table. Reconcile missing entries only after a complete valid scan; finish run state and commit atomically.
8. Disable the progress handler and end the source read transaction with ROLLBACK on both success and failure. This releases the read view; no source write transaction was started. Connection closure removes its TEMP tables.

No full-source snapshot or private JSON output is created. Temporary numeric asset keys and local metadata working files are allowed. OS swap/crash dumps and SQLite's own WAL/SHM coordination are outside an application guarantee of zero disk interaction.

## Synchronization semantics

Identity is (Apple store UUID, entry UUID), not source row number. Raw Apple dates remain seconds since 2001-01-01 UTC; observation/run times use Unix seconds. Source row keys are only used transiently to associate assets.

All entries are scanned each run, including drafts and deletion flags. Fingerprints include linked asset records, not external attachment bytes. An unchanged entry gets a refreshed last_seen_at; changed counts reflect fingerprint/deletion differences. Old store namespaces are retained when a store UUID changes. Removed/restored entries update deletion state without deleting metadata history.

SQLite's source read transaction keeps entry and asset observations consistent while another WAL connection writes. A concurrent change is seen on the next scan. The metadata transaction uses BEGIN IMMEDIATE to serialize index writers. Cancellation, timeout, duplicate/invalid UUID, schema failure or query failure aborts the scan; no incomplete deletion reconciliation is committed. Failure records use fixed codes only. Early source/setup failures may occur before a metadata run exists.

No source timestamp watermark or resumable cursor is assumed. Retry restarts the full scan. A committed metadata index reflects the completed source read view, not necessarily edits arriving after that view was established.

## Responsiveness, resource limits and tradeoffs

ReaderView uses Task.detached for source reading, key ordering, hashing and local SQLite writes. MainActor handles counts every 250 entries and final status only. Awaiting completion suspends the UI task. A sync disables the Sync button; Cancel cancels the worker. Other callers must also keep this synchronous API off the main thread.

JournalReader(sourceURL:maximumReadDuration:) accepts a read budget, default 60 seconds. SQLite VM work checks interruption every 1,000 operations; row stepping checks the deadline/cancellation too. This is cooperative, not a hard real-time wall-clock guarantee: a filesystem stall, busy wait (up to the configured five-second SQLite timeout), one large blob/hash operation, or metadata initialization/commit can delay responsiveness. The source transaction is released in deferred cleanup. Very large stores may repeatedly exceed the budget; a caller can deliberately increase it, accepting longer checkpoint retention. There is no automatic retry loop that holds Journal indefinitely.

Streaming avoids an array of all bodies, but full scans still cost O(source content size), numeric key sorting/indexing, and indexed metadata writes. TEMP numeric key disk usage scales with asset count. Available disk space and peak-memory profiling are not implemented. No metadata schema migration is needed for this reader change. Run history retention is still manual.

WAL normally permits readers alongside a writer, but a reader can hold back checkpoint progress and WAL reclamation. Rollback-journal sources can impose stronger write-lock contention. The app never changes Apple's journal mode, starts a checkpoint or disables normal locking. Read-only open may fail if SQLite cannot obtain the required sidecar access; failure is reported safely with no copy fallback.

## Metadata schema

- sources: store UUID, first observation, last successful synchronization.
- entries: source UUID + entry UUID, source dates, HMAC fingerprint/version, deletion flag, first/last observation and last change.
- sync_runs: run UUID, timing, status, counts and safe error code.
- settings: private per-index HMAC key. It is stored with the index, so database access exposes the key as well as fingerprints.
- scan_seen: metadata-only working UUIDs, cleared after a completed transaction.

No body, title, attachment paths/files, previews, embeddings or summaries. File/directory permissions remain 0600/0700. Existing old text-sample exports are not opened, migrated or deleted.

## Verification and remaining limits

26 synthetic tests pass, including concurrent WAL writes remaining invisible until the next scan, source write rejection, deadline failure preserving the prior index, fingerprint compatibility, cancellation, private metadata, deletion/restoration and 10,000 entries/assets. The live verification observed zero changes on repeat sync and unchanged source database and WAL contents. SHM bytes are not promised unchanged.

Apple private-schema upgrades, million-entry resource behavior, live checkpoint pressure, full-disk errors and macOS permission denial remain operational limits. No real Journal entries were edited for tests. Tests use isolated synthetic stores.
